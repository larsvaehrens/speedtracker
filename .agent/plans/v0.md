Build “SpeedTracker,” a mobile-first web app for tracking our local SpeedRunners games.

We play together on one Nintendo Switch, in front of the same television. This app is a companion scorekeeper and statistics tracker. It does not integrate with the game or automatically detect results.

PRODUCT PRIORITY

The most important feature is extremely fast, reliable score entry.

SpeedRunners is fast-paced. Once a map is revealed, we have only a few seconds before gameplay starts. Users must not have to navigate through forms or complete unnecessary setup during that window.

Prioritize:
1. Fast match setup and score entry.
2. Correct scoring and durable match history.
3. Live synchronization for participants.
4. Useful statistics.
5. Visual polish.

The primary device is a phone. Desktop support is secondary, but the app must remain responsive.


WORKFLOW BEFORE IMPLEMENTATION

First:
- Inspect the existing repository, assets, configuration, and package versions.
- Summarize the proposed architecture and implementation plan.
- Identify any unresolved gameplay rules or incompatible technical requirements.
- Ask focused questions about decisions that materially affect scoring or data integrity.
- Do not silently invent gameplay rules.

Then implement in small, working increments.

Avoid unnecessary infrastructure and speculative features. Favor a maintainable MVP over a complex platform.


TERMINOLOGY

Use these terms consistently in the UI, code, database, and documentation:

- Player: a registered user.
- Competitor: either one solo player or a two-player team.
- Round: one elimination round that awards points.
- Match: a contest on one map, ending when a competitor reaches its victory threshold.
- Setup: the selected players and their competitor/team assignments.

Match history and match win rates refer to completed matches, not individual rounds.


GAMEPLAY AND SCORING

Support 2–4 distinct players.

Supported competitor arrangements:
- 1 vs. 1
- 1 vs. 1 vs. 1
- 1 vs. 1 vs. 1 vs. 1
- 2 vs. 2
- 1 vs. 2
- 1 vs. 1 vs. 2

Do not allow a player to appear in more than one competitor.

Known scoring rules:
- A solo competitor earns one point for winning a round.
- A solo competitor needs three points to win a match.
- A two-player team needs four points to win a match.
- If only one teammate survives the winning round, award that player one point and the team one point.
- If both teammates survive the winning round, award each player one point and the team two points.
- In mixed formats, each solo competitor still need three points to win while the team needs four points to win.
- A team wins immediately when its total reaches or exceeds four.
- There are no tied rounds, no-score rounds, or other scoring exceptions to support.

Store round results and individual point attribution, not just final totals. Scores, outcomes, and contribution statistics must remain consistent with those records.

A completed team victory counts as a match win for both teammates. Individual point contribution is tracked separately.


MATCH SETUP

Allow the signed-in user to:
- Select themselves and friends as participants.
- Assign players to supported competitor arrangements.
- Start a match without selecting a map.
- Quickly reuse the previous setup.
- Completely reset the setup.

Make recent competitors easy to select. Prefer recent participants for the MVP rather than adding multiple recommendation systems.

Persist the previous setup locally if useful, but:
- Scope it to the signed-in user.
- Validate it before reuse.
- Do not automatically start a match from restored data.
- Provide an obvious reset action.

LIVE SCOREKEEPING UI

Keep the current map, competitors, scores, and scoring actions easy to see.

For a solo competitor:
- Show their avatar and screen name.
- Provide a prominent action to award one round win.

For a two-player team:
- Group both players visually as one competitor.
- Show each player’s avatar and screen name.
- Provide an action below each player to award that player one point.
- Provide a separate team-wide action to award both players one point each.
- Show the team total as well as individual contributions.

Score entry should require one tap once the correct action is visible, without a routine confirmation modal.

Provide a prominent undo-last-result action to recover from accidental taps.

Prevent duplicate round creation from rapid taps, retries, or network reconnection. Do not accept further scoring after a match has been completed unless the user explicitly returns it to an editable state through a supported correction flow.

Keep player/team assignments fixed once scoring begins. If changing them is necessary, require a clear restart or reset rather than silently reinterpreting existing results.

Make it possible to abandon a match without treating it as a completed loss.


ACCOUNTS, FRIENDS, AND ACCESS

There is no marketing landing page. Signed-out users see sign-in and sign-up.

Authentication:
- Username and password.
- Username is the login identifier.
- Screen name is a separate editable display name.
- No email service is required.
- Email-based account recovery is outside the MVP.
- Clearly document the consequences of not providing account recovery.

Use established authentication and password-handling components where practical. Do not invent password cryptography.

Implement appropriate password hashing, session protection, server-side authorization, and basic abuse protection for authentication.

Friends:
- Users add/follow another user by exact login username.
- No approval or friend-request workflow.
- Treat this as a one-way follow unless there is a concrete reason to require mutual following.
- Following someone does not grant access to all of their private data.

The match creator can select themselves and followed users as participants.

Recommended MVP permission model:
- The match creator is the scorekeeper and can edit the match.
- Other participants can view its live state and completed results.
- Unrelated users cannot read or modify private matches.
- Enforce these rules server-side, not only in the UI.


SIGNED-IN FEATURES

Provide:
- Start/create match.
- Recent match history.
- Statistics.
- Friend list and add-by-username.
- Profile settings.

Match history should show:
- Map.
- Participants and team arrangement.
- Final scores and outcome.
- Whether the current user won or lost.
- Match duration.

Define duration as elapsed time from starting the match to completing it. Pausing and active-play time tracking are outside the MVP.

Profile settings:
- Change screen name.
- Select an avatar from ressources/heroes/.

Keep username changes outside the MVP unless they are straightforward and necessary.


STATISTICS

Use completed, non-abandoned matches only. Define calculations explicitly and show sample sizes.

Required statistics:

1. Overall match win rate
   - Match wins divided by completed matches played.
   - Team victories count as wins for both teammates.

2. Win rate by map
   - Rank maps from best to worst.
   - Show wins, matches played, and win rate.
   - Maps with no matches should not appear as 0% losses.

3. Performance against opponents
   - Include only matches where the other player was on an opposing competitor.
   - Exclude matches where they were a teammate.
   - Show wins, losses, matches played, and win rate.

4. Performance with teammates
   - Rank two-player partnerships involving the current user.
   - Show team wins, completed matches, and win rate.

5. Team contribution
   - Use individually attributed points.
   - Show each teammate’s points and share of the team’s points.
   - “Both survived” contributes one point to each teammate.
   - Present this as contribution, not an objective skill rating.
   - Handle zero-point totals without division errors.

6. Streaks
   - Current winning or losing streak.
   - Longest historical winning streak.
   - Longest historical losing streak.
   - Calculate in completed-match order with deterministic tie-breaking.
   - Abandoned matches do not count as wins or losses.

Use clear empty states. Avoid implying that rankings based on one match are reliable; show the underlying sample size. Show absolute numbers and percentages where relevant.


SYNCHRONIZATION AND DATA INTEGRITY

A participant should be able to open the app on another device and see:
- Current participants and teams.
- Selected map or missing-map state.
- Current scores.
- Match completion.

Choose a synchronization approach appropriate for Cloudflare Workers and this app’s scale. Do not assume a particular real-time technology is required.

Specify the expected update latency and connection behavior in the implementation plan.

The server is authoritative for results. Handle stale clients and duplicate submissions safely.

If a connection fails:
- Make the connection/save status visible.
- Do not silently lose results.
- Do not show an unconfirmed result as durably saved.
- Refresh authoritative state after reconnection.

A full offline-first system is not required for the MVP.


TECHNICAL PREFERENCES

- Use pnpm.
- Use TypeScript 7 if a suitable supported release is available and compatible with the chosen stack.
- Use Vite+ and its applicable tooling, including Oxc/Oxlint and formatting, where supported.
- Verify exact package names, versions, and compatibility rather than assuming them.
- If a requested tool is unavailable or incompatible, explain the issue and propose the smallest reasonable alternative before proceeding.

Frontend:
- React.
- A mobile-first application.
- A framework such as TanStack Start or Next.js is acceptable if it fits Cloudflare Workers.

Architecture:
- Prefer one application deployment with integrated server-side functionality.
- Avoid a separately maintained REST backend.
- Server functions, route handlers, or equivalent integrated APIs are acceptable.
- Choose the framework based on supported Cloudflare deployment and maintainability, not on an assumption that server components eliminate server-side requirements.

Hosting:
- Cloudflare Workers.
- Custom subdomain, for example speedtracker.example.com.

Authentication:
- Better Auth or another established solution that supports username/password and the chosen runtime.
- WorkOS is acceptable only if it supports the required flow without unnecessary external services.

Styling:
- Tailwind CSS or custom CSS; choose one consistent approach.
- Use accessible contrast, clear focus states, and comfortably sized touch targets.
- If it makes sense, use a primary, secondary, tertiary, and quaternary color palette, which is easy to update later if I want to change the color scheme to be more like the game.

Database:
- ORM or raw SQL is acceptable.
- Choose a Cloudflare-compatible database like D1 with straightforward local development and migrations.
- Provide reproducible schema migrations and map & user seed data.
- Preserve participant/team membership and round attribution in the data model.

Assets:
- Keep map images and avatars in the application’s static assets.
- No blob-storage service is required.
- Preserve the existing ressources directory spelling unless intentionally migrating it.
